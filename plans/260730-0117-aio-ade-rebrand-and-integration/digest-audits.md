## AUDIT: Agent roster reduction: 34 TuiAgent members down to claude + codex (plus decision on Claude-family variants)

### SUMMARY
Reducing 34 TuiAgent members to `claude` + `codex` touches ~120 files. The union in src/shared/types.ts is the keystone: 8 shared modules use `Record<TuiAgent, …>` or `satisfies Record<TuiAgent, …>`, so narrowing the union FIRST makes every stale roster entry an immediate excess-property error, giving you a compiler-driven worklist. On the Claude-family variants: drop both `claude-agent-teams` and `openclaude`. `claude-agent-teams` is not a separate binary — it detects via the `orca` CLI and launches `orca claude-teams`, i.e. it depends on the src/cli tree being deleted. `openclaude` is a distinct third-party binary, not Anthropic's Claude Code. ### GOTCHAS
- Narrow the union FIRST, not last — the opposite of the usual advice. The instinct is to narrow last so typecheck stays green while cleaning up. Here that backfires: the roster is enforced almost entirely by `Record<TuiAgent, …>` and `satisfies Record<TuiAgent, …>`, so while the union is wide, deleting a roster entry is itself the error (missing property). You cannot delete anything incrementally without going red. Narrowing first inverts it: leftover entries become excess-property errors the compiler enumerates for you, and every deletion moves monotonically toward green. Accept one large red window between steps 2 and 3 rather than fighting the type system in both directions.
- `claude-agent-teams` is NOT just another Claude flavor — it is an Orca-hosted launch mode. Its TUI_AGENT_CONFIG entry has detectCmd 'orca' with aliases ['orca-dev','orca-ide'], detectRequiredCommands ['claude'], detectUnsupportedRuntimes ['win32','wsl'], launchCmd `orca claude-teams`, promptInjectionMode 'stdin-after-start', and launchCmdByPlatform built from getOrcaCliCommandNameForPlatform(). Keeping it forces you to keep the src/cli claude-teams entrypoint you are deleting, plus claude-agent-teams-tmux-compat.ts and the native-pane/tmux-shim machinery. It looks like a one-line keep and is not.
- `openclaude` reads as Claude-family but is a distinct third-party binary (detectCmd/launchCmd/expectedProcess all 'openclaude', with its own `--prefill` flag). 'Claude Code + Codex only' should exclude it.
- Agent ID does not equal binary name, so grepping the id misses call sites and grepping the binary misses the id. Real mismatches in TUI_AGENT_CONFIG: kiro→`kiro-cli chat --tui`, aug→`auggie`, continue→`cn` (because `continue` is a shell builtin), cursor→`cursor-agent`, qwen-code→`qwen`, mistral-vibe→`vibe` (with 'mistral-vibe' as an alias), antigravity→`agy`, mimo-code→`mimo`, trae→`traecli` (deliberately, to avoid colliding with the unrelated bytedance/trae-agent `trae-cli`), command-code→`command-code` (full name chosen to avoid Windows cmd.exe). Sweep BOTH id and binary for each removed agent. `agy` and `cn` are short enough to produce false-positive grep noise.
- `isTuiAgent()` in src/shared/tui-agent-config.ts is a runtime guard over `Object.prototype.hasOwnProperty.call(TUI_AGENT_CONFIG, value)`. It silently starts returning false for removed ids the moment you trim the table — correct, but it means stored values now flow down whatever the `else` branch is at each call site. Audit those branches: some may throw or render blank rather than falling back to claude.
- Do NOT delete the `?? 'other'` fallback in `tuiAgentToAgentKind` (src/shared/agent-kind.ts). Its comment states the exact reason it exists: stale persisted settings or unsafe IPC casts can carry an out-of-union string. After the reduction there will be MORE such strings in the wild, not fewer. Same for `agentKindToTuiAgent` returning null.
- src/shared/agent-session-option-catalog-claude-codex.ts vs -gemini-cursor.ts is a trap for automated cleanup: the filenames suggest a symmetric pair, so a script that deletes 'the other catalog' could grab the wrong one. The claude-codex file is exactly what you keep.
- The `droid` removal reaches further than the roster: TUI_AGENT_CONFIG['droid'] carries `windowsShiftEnterEncoding: 'csi-u'`, which is why the Windows Shift+Enter branch exists at all (src/renderer/src/components/terminal-pane/terminal-windows-shift-enter.test.ts). Droid also owns the droid-orchestration-group doc and appears in src/main/runtime/orchestration/groups.test.ts (45 hits). Deleting the agent leaves an orchestration group and a keyboard-encoding code path orphaned in different layers.
- Delete mobile/ and src/cli/ BEFORE the roster work, not after. mobile/src/tasks/mobile-tui-agents.ts (91 hits), mobile-agent-catalog.ts, mobile-agent-icon-assets.ts, MobileAgentIcon.tsx, accounts-snapshot.ts, agent-row-display.ts and ~15 more mobile files all enumerate the roster. Editing then deleting them is pure waste, and mobile/ has its own pnpm-lock.yaml (52 hits) so it is a semi-independent workspace.
- Test-file hit counts are a better effort estimate than source-file counts, and they invert the usual ratio: pty-connection.test.ts 229 vs 53 in the source; orca-runtime.test.ts 224 vs 197; server.test.ts 271 with no comparably sized source. The bulk of this task is fixture-table maintenance, not production logic.
- resources/ images and per-agent CSS are easy to forget because nothing type-checks them. src/renderer/src/assets/main.css has 34 agent-token hits (brand colors/icon classes) and will not error when an agent disappears — it just accumulates dead rules. Same for orphaned images.

### RISKS
- Persisted settings rejection is the highest-severity risk. `defaultTuiAgent`, `disabledTuiAgents`, `agentCmdOverrides`, `selectedModelByAgent` carry agent ids into src/main/persistence.ts (65 agent-token hits). If those fields are validated with a zod enum derived from the narrowed roster, every existing user profile containing e.g. 'gemini' fails validation. Depending on how persistence handles a parse failure, the blast radius is either a crash on boot or a silent reset of ALL settings, not just the agent field. Handle with a coercing migration, not schema narrowing.
- Telemetry enum narrowing would break historical validation. `agentKindSchema = z.enum(AGENT_KIND_VALUES)` in src/shared/telemetry-events.ts feeds agentStartedSchema and agentPromptSentSchema, both `.strict()`. Narrowing it means any locally queued or retried event referencing a removed kind now fails validation and is dropped. Leave AGENT_KIND_VALUES wide; only trim the TuiAgent→AgentKind map.
- src/main/runtime/orca-runtime.ts (197 hits) + orca-runtime.test.ts (224), src/renderer/src/components/terminal-pane/pty-connection.test.ts (229), and src/main/agent-hooks/server.test.ts (271) are dense enough that a hurried find/replace will introduce logic errors. These four files alone are a meaningful fraction of the total effort.
- i18n key drift: five locale files carry agent keys at different counts (en 73, es 76, ja 53, ko 48, zh 49). The counts already differ, so the locales are not perfectly aligned today. Deleting keys unevenly will either leave orphans or break a key-parity check. config/scripts/locale-ko-key-overrides.json is a third source of truth for ko.
- Deleting resources/ image assets can break the build if any module imports them via a bundler glob (Vite `import.meta.glob`) rather than an explicit path. Check src/shared/agent-icons/ and src/renderer/src/lib/agent-favicon-assets.ts for glob patterns before bulk-deleting images.
- src/renderer/src/lib/orchestration-skill-coverage.test.ts asserts skill coverage across the roster. It will fail after reduction and its failure mode is a coverage assertion, easily mistaken for a missing-skill bug rather than expected roster shrinkage.
- Removing per-agent main directories may break relay plugin-overlay wiring: src/relay/plugin-overlay.ts (32 hits) + .test.ts (88 hits) install overlays such as the pi titlebar extension and the orca-prefill extension. The ORCA_PI_PREFILL / ORCA_OMP_PREFILL env-var seeding disappears with pi/omp, but claude uses the `--prefill` FLAG instead, so no prefill capability is lost for the kept agents.
- Scope creep with the brand rename. `orca` appears in 3475 files and the agent code is saturated with it (ORCA_PI_PREFILL, getOrcaCliCommandNameForPlatform, orca-runtime.ts, detectCmdAliases ['orca-dev','orca-ide']). Doing roster reduction and rename in one pass makes conflicts and review nearly impossible. Land roster reduction first, rename second.

Rough split: shared type/data tables ~2h (8 files, mechanical once the union is narrowed); per-agent directory deletions ~1h; main-process surgical pass ~4-6h (orca-runtime.ts at 197 hits dominates); persistence migration + tests ~2-3h (highest risk-per-line, do not rush); renderer pass ~4-5h (agent-catalog.tsx, status-bar family, automations); assets/CSS/i18n ~2h; test rewrites ~6-8h (the five 100+ hit fixture tables are the single largest bucket); docs/skills ~2h. Renaming it does not error — readManagedClaudeKeychainCredentials() just returns null, which the code path treats as 'no credentials', so users silently get logged out with no diagnostic. ### GOTCHAS
- `src/relay/plugin-overlay.ts` and the `hook-plugin-*.ts` files under `src/main/opencode/` match a `plugin` grep and are full of `orca` literals (`.orca-relay`, `orca-opencode-status.js`, `@orca-managed-pi-extension`), but they belong to the agent-status overlay system, not the plugin system. Touching them in a plugin-surface change breaks SSH agent status.
- Of the ~138 `orca` literals inside plugin-named files, the heaviest concentrations are tests and fixtures (`plugin-install.test.ts`: 53, `skill-plugin-cache-scan.test.ts`: 121). Raw grep counts wildly overstate the production surface — the real contract is about six constants in three shared files.
- `PLUGIN_HOST_API_V0` is the single source of truth for three things at once: the capability gate, the panel-callable action allowlist (`PLUGIN_PANEL_ACTIONS` is derived by filtering `panel: true`), and the worker SDK. Adding or renaming a method there changes what sandboxed panels may call, which is easy to do accidentally.
- `readPanelPongId` is a hand-rolled mirror of `panelPongSchema`, written that way because a failed zod parse allocates an issue list (~90x the accept path) and a hostile panel can spam near-miss pongs. Replacing it with `safeParse` for tidiness reintroduces a DoS vector.
- The panel shell prepends the CSP `<meta>` before any plugin markup, and `fillPanelShell` uses first-occurrence `String.replace`. That ordering is what makes a plugin echoing the placeholder string inert — switching to `replaceAll` or moving the fill after plugin content would let a plugin inject its own tokens.
- The renderer keys the panel iframe on `${tabKey}:${documentRevision}:${themeRevision}`, and `right-sidebar-panel-content.tsx` also keys `<PluginPanel key={effectiveTab}>`. Both are deliberate: a reused frame could keep posting messages while the bridge is rebound under the next plugin's identity. Dropping either key looks like a harmless remount optimization and creates a cross-plugin authority bug.
- `resolvePluginPanelIcon` uses `Object.hasOwn` so a manifest icon named `constructor` cannot resolve to an inherited member and crash the sidebar. The same defensive pattern appears in storage keys (`RESERVED_STORAGE_KEYS`), plugin ids (`DANGEROUS_PLUGIN_NAMES`), and `isTopLevelView` — treat prototype-key rejection as a house invariant, not local paranoia.
- There is a `generate:bundled-skill-guides` and a `generate:skill-bundle-manifest` script but no bundled-plugin equivalent, so the `contentHash` in `bundled-plugins.json` has to be regenerated by hand or by a new script. It is the one place in this change with no CI safety net until bootstrap fails at runtime.
- AGENTS.md bans `max-lines` disables outright and `config/max-lines-baseline.txt` may only shrink, yet several files you must edit are near their budget (`right-sidebar/index.tsx` already carries a grandfathered disable at 543 lines). Plan for a split, not a suppression.
- `plugin-error-presentation.ts` matches error text by substring (`detail.includes('orca-plugin.json')`). Renaming the manifest filename without updating that matcher degrades every install failure to the generic message, which reads as a UX regression rather than a missed rename.

### RISKS
- Renaming `orca-plugin.json` or `engines.orca` without a read fallback fails manifest parsing wholesale — every installed plugin, every marketplace listing, and the three bundled packs become `invalid` at once, and the failure surfaces as a generic settings-row error rather than a migration prompt.
- Changing the four `orca-panel-*` postMessage strings is a silent break for third-party panels: the host deliberately ignores messages whose `type` it does not recognize (`looksLikePanelActionRequest`), so an old panel simply stops working with no error anywhere.
- `PLUGIN_PANEL_FRAME_NAME_PREFIX` is a security boundary, not a label. The main-process navigation registry binds frames by that name at `frame-created`, before plugin script can mutate `window.name`. If the renderer's iframe `name` and the guard's prefix diverge, navigation containment fails open while every happy-path test still passes.
- Any byte change inside a bundled plugin tree invalidates the pinned `contentHash` in `bundled-plugins.json`; bootstrap rejects the mismatch and the bundled navigation-shortcuts pack disappears silently on a fresh profile.
- Content-hash changes also flow into `canonicalizePluginConsent` for instructional packs (keybindings/vmRecipes/agents), so renaming files inside those trees re-prompts consent for existing users and leaves their panels disabled until they re-approve.
- The persisted right-sidebar route stores `plugin:<publisher>.<id>/<panelId>`. Rebranding publisher/id strings orphans those keys, and `normalizeRightSidebarRoute` resets unknown-shaped keys to Explorer without telling the user their pinned panel is gone.
- Localization is CI-gated in both directions: `verify:localization-catalog` (key/placeholder parity across en/es/ja/ko/zh) and `verify:localization-coverage` (allowlist of unlocalized renderer strings). Editing plugin settings copy without running the sync script fails PR checks even though the code is correct.
- The subsystem ships off (`pluginSystemEnabled: false`), so a regression can pass a full manual smoke test and land unnoticed; verification must explicitly enable the flag.

### ESTIMATE
Cosmetic-only pass (dirs, sample plugin, docs, i18n, bundled-tree rename + hash regen): roughly half a day plus a bundled-hash helper script. Full contract rename with accept-both shims for the manifest filename, `engines` key, and the four panel wire strings, including the atomic frame-name/placeholder change and updated e2e containment fixtures: 2-3 days, with the bundled `contentHash` regeneration and the consent-refingerprinting fallout as the two items most likely to slip.
